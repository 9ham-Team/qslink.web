# QSLink 前端框架选型与迁移评估报告

评估日期：2026-11-13。代码基线：`0134fa4c90be76f2cf4e73def08acbea0fd914cb`（本地分支 `codex/contest-auto-entry`）。

本报告根据当前检出的实现、项目契约和官方框架文档编写；未刷新远端引用，不能代表此后团队 `dev` 的变化。本次只新增评估文档，没有安装框架、修改应用、执行迁移或发布。框架建议与工期属于工程判断，性能结论需经原型测量。

## 1. 结论与决策条件

**在 Vue 与 React 之间，推荐 Vue 3，采用 Composition API、单文件组件（SFC）和 Vite，逐页迁移现有 SPA。** 配合 Vue Router 管理路由；跨页面会话状态可使用 Pinia。Node.js HTTP 服务、PostgreSQL、Sharp、API 和既有 CSS 设计系统继续承担现有职责。

主要依据：QSLink 的复杂度集中在表单、审核、换卡、赛事和异步页面状态；当前大量 HTML 字符串、手动 DOM 更新与事件绑定，更容易逐步转换为 Vue 模板、响应式状态和 composable。Vue 的模板与现有 HTML/CSS 接近，适合先保留样式和领域逻辑、再替换页面组织方式。React 同样能够完整实现这些功能，但本仓库没有 React 组件或专属生态资产可以抵消转换 JSX、梳理状态和副作用的成本。

这不是必须立即启动全站重写的结论。若近期只有小规模维护，继续原生架构并拆分大模块，短期投入更小。若未来持续扩展赛事、管理后台和复杂表单，Vue 迁移才更有长期价值。第一步应做有明确退出条件的原型，再决定全面投入。

推荐成立的假设是：团队没有明显的 React 熟练度优势，也没有近期 React Native 或 React 专属组件平台需求。团队实际经验尚未访谈确认；若维护者已经熟悉 React、缺少 Vue 经验，应重新比较培训和维护成本，React 可能成为更合适的选择。

**不能据此承诺：迁移后首屏一定更快、包体一定更小、SEO 自动改善、手机 3D 闪烁自动消失。** 两种框架都增加运行时代码；首屏收益主要取决于是否拆分当前全量加载的脚本，以及是否避免重复渲染和多余请求。

## 2. 当前实现与迁移价值

### 2.1 代码证据

以下数量来自本次本地静态统计，不是网络传输或浏览器性能数据。

| 现状 | 证据 | 对迁移的影响 |
| --- | --- | --- |
| 原生 SPA，无前端构建 | [package.json](../package.json)、[index.html](../public/index.html)、[前端契约](../docs/CONTRACT.md) | 需要新增构建、锁定依赖和产物部署流程；这是明确的新增维护成本 |
| 22 条路由记录 | [core.js](../public/js/core.js) 的 `QSL.routes` | 必须保持深链接、别名、查询参数、锚点、登录回跳和权限行为 |
| 页面目录有 20 个 JS 文件，共 558,815 字节 | [pages](../public/js/pages) | 包含后台评审子模块；文件数不等于独立路由页数，多条路由会复用页面 |
| HTML 入口显式引入 34 个脚本 | [index.html](../public/index.html) | 包括后台与赛事；支持后续按路由延迟加载，但现有脚本可被浏览器缓存，不能把源码体积当作每次实际下载量 |
| 后台约 122 KB，换卡约 56 KB，编辑器约 49 KB（源码） | [admin.js](../public/js/pages/admin.js)、[exchanges.js](../public/js/pages/exchanges.js)、[card-editor.js](../public/js/pages/card-editor.js) | 页面承担多种状态、模板和弹窗逻辑，适合按业务区域组件化 |
| 共享状态与事件总线 | `QSL.state`、`QSL.setUser`、`QSL.on/emit` | 需要单一会话来源，避免新旧用户状态不同步 |
| 页面有显式清理契约 | `render(container, ctx)` 返回 cleanup；页面使用存活标志与请求序号 | 框架生命周期有助于集中清理，但不会自动取消网络请求、销毁 Worker 或释放外部监听 |
| 编辑器临时包装全局导航函数 | [card-editor.js](../public/js/pages/card-editor.js) 的未保存守卫 | 可迁到组件路由离开守卫；浏览器关闭、语言重载仍需单独处理 |
| 3D 和图片处理已模块化 | [card3d.js](../public/js/card3d.js)、[images.js](../public/js/images.js)、[image-upload.js](../public/js/image-upload.js) | 优先适配复用，避免把高频动画和业务迁移绑在一起 |
| 六份 CSS，已有 tokens 和模块前缀 | [css](../public/css) | 第一轮保持类名和层叠顺序，降低视觉回归 |
| 已有后端测试、部分前端模块测试及 CDP 脚本 | [tests](../tests)、[run-tests.mjs](../tools/run-tests.mjs) | 可以保留业务基线，但要更新依赖源码路径和全局对象的测试，并把关键浏览器用例接入 CI |

### 2.2 应解决的问题

- 用组件与局部状态表达加载、空、失败、提交和成功状态，减少同一操作中多处手动修改 DOM。
- 将库存弹窗、选卡、附通联记录、确认框、分页、作品状态等重复交互变为共享组件。
- 将请求过期处理、取消、表单错误映射与资源清理做成可复用逻辑，减少页面重复实现。
- 将后台、赛事和编辑器从公开入口的立即执行路径中拆开；是否获得首屏收益由同条件测试决定。

目前没有运行数据证明原生架构本身造成性能瓶颈，也没有缺陷统计量化维护成本。本报告识别的是代码组织上的迁移机会。

## 3. Vue 与 React 的针对性比较

比较对象是 Vue 3 + Vite 与 React + Vite 的客户端方案。两者均可增量接入已有站点，均可保留当前后端；不把 React 等同于 Next.js，也不把 Vue 等同于 Nuxt。

| 维度及本项目优先级 | Vue 3 | React | QSLink 判断 |
| --- | --- | --- | --- |
| 现有 HTML/CSS 迁移成本：高 | 模板接近现有结构，事件、条件和列表可渐进替换 | JSX 需要转换属性及模板表达方式，状态也需重新组织 | Vue 更便于保持现有页面结构；二者都需要重新设计状态，不能机械转换 |
| 表单及业务状态：高 | `v-model`、computed、composable 适合编辑器、筛选与审批 | state、受控输入、自定义 Hook 同样成熟 | Vue 对当前表单密集页面更直接；双方都可完成字段错误与防重复提交 |
| 命令式 3D 与资源清理：高 | 模板 ref + 挂载/卸载钩子包装既有引擎 | ref + Effect 也可包装；需正确处理依赖与清理 | 能力接近；关键是 DOM 所有权和幂等销毁。React 开发 Strict Mode 会额外检验 Effect 的 setup/cleanup，不是生产必然重复创建 |
| 异步数据与权限：高 | 路由守卫、watch、AbortController 与请求序号 | 路由方案、Effect/Hook、AbortController 与请求序号 | 能力接近；服务端仍是权限边界，二者都不会自动避免竞态 |
| 路由与全局状态选择：中 | Vue Router、Pinia 提供较统一的配套选择 | 需选择客户端路由及状态方案；组件局部状态也可满足许多场景 | Vue 更容易让本项目统一约定；React 不要求必须引入 Redux |
| 动画和运行性能：高 | 可让外部引擎独立运行，支持代码拆分 | 同样可独立运行和代码拆分 | 无实测胜者；不得每帧触发应用状态更新 |
| 生态和未来跨端：中，尚未确认需求 | Web 业务生态足够 | React 生态与 React Native 是潜在优势 | 当前未见必须依赖 React 的功能；若跨端成为明确目标，重新评估 |
| 工具链与持续交付：中 | Vite、组件测试、浏览器测试 | 相同类别工具均成熟 | 两种方案都要改造当前无构建的 CI 与 Docker |
| 团队长期维护：高，信息不足 | 需确认 Vue/Composition API 熟练度 | 需确认 React/Hooks 熟练度 | 团队经验可覆盖上面的语法迁移优势；不能根据网站语言推断开发者技能 |

不采用“社区规模”或“虚拟 DOM 更快”等泛化理由决定选型，也不以人为加权分数冒充测量结果。**当前推荐 Vue 的决定因素是现有代码的转换成本和业务组织方式，而非 React 无法胜任。**

## 4. 推荐目标架构

### 4.1 技术组合与范围

| 层 | 推荐 | 约束 |
| --- | --- | --- |
| 页面与组件 | Vue 3，Composition API，SFC | 页面拆为展示组件与业务 composable；复用现有 CSS |
| 构建 | Vite，Vue 插件 | 开发工具依赖安装在构建阶段；生产只部署静态产物 |
| 路由 | Vue Router，history 模式 | 保持全部现有 URL；页面按需 import；迁移期遵守单一路由所有权 |
| 状态 | 页面本地 ref/reactive；会话与配置按需用 Pinia | 不把表单草稿、所有服务端数据或动画角度全部放入全局 store |
| API | 现有 API 客户端先适配、再模块化 | 保留 `ApiError`、字段错误、401、Bearer 与 AbortSignal 语义；不为迁移改鉴权模型 |
| 语言 | 适配现有词典、翻译与错误映射 | 第一轮保留语言重载行为、偏好优先级及法律页双语链接 |
| 类型 | 新服务边界和新组件逐步使用 TypeScript | 不一次性转换后端或整个遗留 JS；类型不能代替服务端校验 |
| 测试 | 保留 Node 测试，新增组件测试及关键浏览器回归 | Vitest / Vue Test Utils 与 Playwright 可在原型期选定、锁版本；不得只补源码文本断言 |

不把 SSR、Nuxt、WebGL、全新 UI 组件库、API 重写或数据库迁移纳入第一轮。若分享平台预览或搜索引擎抓取有明确缺口，应独立评估元信息或预渲染，框架替换本身不解决这些需求。

具体依赖版本应在实施时确认兼容性并写入锁文件。本报告不指定未经验证的最新版本。当前声明 Node.js ≥20.9，CI/生产使用 24；选定 Vite 可能提高本地构建版本下限。建议统一以 Node 24 构建并同步说明，不能继续默认所有 ≥20.9 的环境都兼容新工具链。

### 4.2 建议目录

以下为规划，不是本次已创建的目录。建议 `client/` 只放新前端源码；现有 `public/` 在过渡期继续保存遗留页面与静态资产。

```text
client/
  index.html
  vite.config.mjs
  src/
    main.ts
    App.vue
    router/
    stores/             # 会话、公共配置
    services/           # API、错误、下载、翻译适配
    composables/        # 异步竞态、表单、离页守卫
    components/         # Modal、Toast、Pagination、CardTile、Card3DViewer
    features/           # cards、exchanges、logbook、contest、admin
    legacy/             # 临时适配入口与迁移清单
dist-public/            # 生成目录，不提交
```

构建输出 `dist-public/`，运行镜像将其复制到现有 `/app/public`，保持服务端静态目录配置。过渡构建须先复制必要的旧 CSS、JS、图片及法律页，再生成入口和新资源，明确顺序与覆盖规则；不允许构建清空唯一的遗留源目录。新 bundle 使用独立资源前缀，例如 `/build/`，避开既有 `/assets/` 品牌资源。

根包保持 CommonJS，Vite 配置使用 `.mjs`；不能为前端 import/export 将根 `package.json` 改为 `type: module`，否则会影响现有服务端。

### 4.3 模块处理方式

| 原有模块 | 迁移方法 | 验收要点 |
| --- | --- | --- |
| `core.js` 路由及事件 | 先保留旧路由，再分离工具/事件/状态，最终由 Vue Router 接管 | `next` 安全校验、guest/auth/admin、404、别名、查询参数、锚点和历史返回 |
| `api.js` | 经适配层暴露给 Vue；完成后提取独立模块 | 新旧共用唯一 token 与用户来源；切换账号清理旧请求及敏感状态 |
| `ui.js` | 逐个迁移，优先表单错误、toast、modal、卡片缩略图 | 焦点恢复、键盘、嵌套 Escape、重复提交、关闭后迟到响应 |
| `card3d.js` | 封装 `Card3DViewer`；初期保留引擎实现 | mounted 创建；卸载 destroy；只在图片/比例等有效变化时调用已有 setter |
| `images.js` | 保留选图规则，逐步提供结构化属性和组件生命周期绑定 | 不直接复用 HTML 属性字符串去拼 Vue 模板；保留布局宽度与 DPR 规则 |
| `image-upload.js` / Worker | 先完整保留同源路径，再独立迁移模块 Worker | 现 Worker 硬编码 `/js/image-upload-worker.js` 且通过 `importScripts` 加载；不能直接当 ESM Worker 打包 |
| `effects.js` | 先适配受控区域，再转换为组件或指令 | 不能反复增强整个 document；移除监听、观察器、计时器及 rAF，尊重减少动态效果 |
| `qr.js`、海报和调色板 | 先复用算法与下载行为，再模块化 | canvas、图片加载、跨域、字体与对象 URL 生命周期 |
| `i18n.js` / 英文词典 | 提供统一 `t` 与错误翻译适配 | 不翻译用户文本/API 枚举；取消语言切换不得提前保存偏好 |
| `app.js` / 法律页 | 最后迁应用外壳；独立法律页继续静态分发 | 导航、公告、版本时间、移动菜单和中英文法律链接均保留 |

## 5. 迁移路径与工期

### 5.1 新旧页面如何共存

第一阶段由现有 `QSL.router` 独占全站 history、链接拦截和路由守卫。选择一条试点路由，将其旧注册实现替换成桥接注册：在页面专属空容器挂载 Vue 应用，返回 `app.unmount()` 作为 cleanup。不要同时执行该页原始注册脚本；其他页面仍照常注册。

现有导航壳、toast、modal、公共背景仍由旧层管理；试点 Vue 只拥有桥接容器及明确划归它的子树。同一个 DOM 区域只能有一个写入者。旧 effects 对 Vue 区域的 DOM 写入应停用或改为显式适配，不能任由全局增强器与组件重复绑定。图片观察器等共享服务需要明确保留范围。

桥接上下文传入路由参数、查询和页面实例标记，通过服务适配访问 QSL，不把 `window.QSL` 变成每个新组件的隐式依赖。原路由异步挂载返回时若页面已失效，必须立即卸载已创建实例，不能只丢弃 cleanup。每个桥接注册、依赖脚本和退回入口应记入迁移清单。

**最终切换时只有 Vue Router 可以启动 history 监听。** 新路由表接管完整路径、外壳和守卫；未完成页面可以通过 `LegacyPageHost` 在独占容器中调用旧 `render` 和 cleanup，但不得再次调用旧 router init。此时 `QSL.navigate` 等遗留调用需委托给 Vue Router，并移除旧链接拦截。避免两个路由器同时响应 popstate 或重复 pushState。

迁移期同一路由参数变化也须清理旧请求、更新页面；不能只依赖组件卸载，因为 `/card/a` 到 `/card/b` 可能复用组件实例。切换前覆盖直接刷新、前进后退及快速跨页，不只测试点击菜单。

### 5.2 阶段、交付物与退出条件

工作量为熟悉项目的开发者的有效工程人日，含相应测试与审查；不是自动转换代码所需时间。未确认人员熟练度和业务并行需求，需原型后校准。

| 阶段 | 内容与交付物 | 退出条件 | 估算人日 |
| --- | --- | --- | --- |
| P0 基线与风险原型 | 记录现有功能与性能；做 `Card3DViewer`、异步列表、一个带未保存提示的表单原型 | 相同设备可对照，能完整清理，明确依赖与回退方法 | 3–5 |
| P1 工程与适配 | Vite、桥接注册、API/会话适配、构建产物、Docker 与 CI | 新旧页能往返；本地与镜像内构建均能提供同源资源 | 5–8 |
| P2 公开只读试点 | 优先迁 `/space/:uid`，再迁广场；抽出卡片缩略图、分页、空/错状态 | 保持显示偏好、排序、分页和移动布局，无旧响应覆盖新页 | 3–5 |
| P3 公共展示与账户 | 首页/公告、详情、分享、登录、注册、个人中心/资料 | 3D、分享与双语回归通过；账户行为和字段错误一致 | 7–11 |
| P4 交易与编辑 | 我的卡片、库存、编辑器、换卡、通联日志 | 图片转换、独立库存保存、附日志、地址权限与未保存守卫均通过 | 10–15 |
| P5 赛事与后台 | 报名、作品/投票、人工评审、后台分区及受保护下载 | 公开/私有材料边界、投票额度、修订冲突与评分规则不变 | 8–12 |
| P6 全站收口 | 切换唯一路由与外壳、删除已无调用的桥接及旧脚本、文档和回归 | 无双路由、无遗留双份状态、构建镜像和发布回退演练通过 | 6–9 |

基础合计 **42–65 人日**；加约 25% 的缺陷、设备兼容与协调缓冲，预算约 **53–82 人日**。单人约 11–17 个有效工作周；两位熟悉项目的工程师可按约 7–11 周日历期规划，最终仍受共享层串行修改、审核和设备验收影响。外部采购设备、业务新增及正式生产发布等待不在此估算内。

若只有时间处理一个页面，不应为此先接管全站路由。若原型发现 3D 生命周期或构建兼容成本明显超出预算，可停止在桥接试点，保留原生方案；不要在缺少证据时扩大重写范围。

## 6. 不可丢失的业务与安全契约

迁移逐页对照 [API](../docs/API.md)、[前端契约](../docs/CONTRACT.md) 及对应服务端实现。至少维护以下回归清单：

- 卡片可见性、编辑重新审核、所有权、管理员与评委权限仍由服务端判定；私有评审图及评分不能进入公开缓存或静态产物。
- 库存保存与内容保存分开；编辑内容不携带过期 stock；同意换卡的扣减和零库存拒绝以服务端返回为准。
- 附通联记录必须用户主动选择，跨页选择保留且不超过现有限制；不能变成自动匹配或自动分享。地址按现有授权阶段显示。
- 图片选取仍依据未旋转的布局宽度与 DPR；3D 查看器最低档 1280、最大候选 3840；旋转时不逐帧写入 src/srcset。
- 图片在本地按既有约束转换 WebP；正反面串行、取消排队、终止 Worker、失败保留已就绪图片、离页不提交原图。
- 赛事投票成功后使用服务端状态更新，不乐观加票；保持全赛期额度、不可撤回及开放时间规则。后台 `expectedRevision` 冲突不能被静默覆盖。
- 鉴权下载保持 Bearer 获取 Blob，不把 token 拼入 URL；关闭和离页回收对象 URL。LoTW 密码不进持久存储或全局状态，提交后和离页清空。
- Vue 模板插值默认转义，但 `v-html`、URL、原生 DOM 和遗留 HTML 拼接仍需边界检查；用户文本与公告正文不能作为模板或可信 HTML 编译。
- 同源 API、上传与本站资源继续工作，不新增 CDN 运行时依赖；公共构建时间、双语法律页、内容授权和注册验证码保持原语义。

## 7. 3D、性能与兼容性验收

### 7.1 引擎边界

Vue 组件只负责容器、低频输入和用户操作；旋转角度、惯性与每帧 transform 留在原生 3D 引擎内部。实例不放入深层响应式状态；挂载后创建，卸载时销毁，图片和比例变化调用已有 setter。第一轮不使用 KeepAlive 缓存动画页；若以后引入，需实现激活/停用时的暂停恢复。

不要给 3D 祖先随意增加 transform、filter、opacity 或新的合成层。这些变化可能影响已有 preserve-3d、背面隐藏及混合效果。拖动过程的闪烁必须记录浏览器、设备、版本与手势，逐变量对照；静置 rAF、接口健康和缩图成功均不能代替拖动视觉验收。

### 7.2 测量方法与建议门槛

P0 保存当前版本在桌面及目标手机的冷/热缓存数据。对照版本使用相同数据量、图片、视口、网络和 CPU 条件；每场景至少重复 5 次取中位数，并记录异常。下列是建议项目门槛，尚未经过团队确认，也不是当前成绩：

| 项目 | 测量与建议验收 |
| --- | --- |
| 首次加载 | 保存首页、广场、详情的压缩 JS/CSS 传输量、LCP、CLS 和请求瀑布；首屏关键资源不得无解释增加超过 10%，不得加载后台/私有评审页面 bundle |
| 页面切换 | 沿用现有契约的本地首次渲染 <150ms 目标，先明确起止点和是否含 API；同时单列路由点击到骨架、数据返回到可操作两段，不把网络等待隐藏在统计外 |
| 真实交互 | 对固定的搜索、弹窗、翻面操作记录延迟与长任务；若有足量真实用户数据，再评估 p75 INP ≤200ms、LCP ≤2.5s、CLS ≤0.1 的用户体验目标，不能用少量实验室操作冒充线上分位数 |
| 资源清理 | 同一组详情→编辑器→列表往返 30 次，检查 rAF、监听、观察器、Worker 与堆快照；离页不得残留该页活动资源，不得出现持续累计的实例或脱离 DOM 节点 |
| 3D 手势 | 真实目标手机快速正反翻转、拖动松手、竖卡/横卡、切后台恢复；不得新增可复现闪烁、触摸滚动冲突或图片请求风暴 |
| 布局与可访问性 | 至少 375px 手机和 1440px 桌面；键盘、焦点、嵌套弹窗、减少动态效果、中英文长文本均可操作 |

建议覆盖目标用户实际使用的 Android Chrome、iOS Safari，以及需要支持的微信内置浏览器版本。构建语法降级不等于补齐 Worker、OffscreenCanvas 或 createImageBitmap 等 Web API，仍要保留能力探测与已有异步回退。

## 8. 构建、测试与部署改造

当前 [Dockerfile](../Dockerfile) 仅安装生产依赖并复制 `public/`；[.dockerignore](../.dockerignore) 为白名单，默认排除新增源码。只执行框架安装会导致源码无法构建或镜像缺少页面，必须同时处理：

1. 新增 builder 阶段，使用锁定依赖并包含构建所需 devDependencies 与 optional 包；运行前端构建。为 `.dockerignore` 显式加入 `client/`、构建配置及所需源码，检查构建上下文不含私密配置。
2. 运行阶段继续安装后端生产依赖，保留 Sharp 的目标平台 optional 包；从 builder 复制 `dist-public/` 到 `/app/public`。不复制 Windows node_modules，不让生产依赖 Vite dev server。
3. 保留当前镜像修订、构建时间、非 root 用户、健康检查和数据卷语义。生成前端与服务端属于同一镜像修订，`/api/config` 元数据与 OCI 标签一致。
4. CI 新增前端构建、适用的类型检查、组件与浏览器回归，保留 `npm test` 和 `npm run test:production`。已有部分测试在 VM 中读取 `public/js` 或检查源码，模块迁移时改为可导入逻辑和行为验证；不能直接删掉失败测试。
5. 当前 CI 没有单独的全站浏览器交互步骤，`tests/forms.mjs`、`tests/console.mjs` 等也有旧演示凭据假设。接入前适配隔离数据与受控账号，不把脚本存在视为持续验收已经覆盖。
6. 验证静态资源 MIME、Worker 路径、直接刷新 SPA 深链接、法律页、品牌资产及上传图。当前服务对带扩展名的不存在路径返回 404，对无扩展名路径回退入口；缺失 chunk 不能被错误返回为 HTML。
7. 初期可保留现有 JS/CSS `no-cache`，后续仅对确有内容哈希的生成资源启用长缓存；HTML 仍需及时更新。部署后旧标签页可能请求旧动态 chunk，需选择保留前一批哈希资产，或提供经用户确认再刷新的恢复流程；有未保存内容时不得自动强刷。
8. 所有构建环境公开变量都可能进入浏览器包；数据库连接、邮件密钥、评审私有数据不得注入。Source map 是否公开应有明确策略，并保证 AGPL 对应源码获取要求得到满足。

实施时在构建产物上运行浏览器验收，不只测试开发服务器。测试仍使用临时 PostgreSQL 或独立测试数据库；前端框架迁移不应要求业务数据库结构变更。

## 9. 发布与回退

每个阶段通过独立功能 PR 进入团队 `dev`。原型试点采用构建配置或明确的路由迁移清单切换旧/新实现，并先验证开关本身；不得依赖隐藏 URL 绕开鉴权。测试服验证后再安排生产发布。

| 风险 | 控制与回退 |
| --- | --- |
| 双路由或双份会话导致重复导航、重复提交 | 每阶段只有一个路由所有者和 token 来源；用快速切页、过期会话和切换账号验证 |
| 3D、Worker、观察器泄漏 | 保留引擎、统一资源作用域、离页与参数变化测试；试点异常退回旧页面注册 |
| 复杂审批或投票规则丢失 | 迁移前建立业务矩阵；服务端规则与测试保持，写操作按服务端结果更新 |
| 构建产物或旧动态 chunk 不完整 | 镜像内验收深链接和资源清单；部署切换策略覆盖旧标签页 |
| 页面迁移期间业务继续修改 | 每阶段限定路由、记录旧新映射；同一业务变更同步相关实现并尽快移除双份代码 |
| 团队不熟悉新工具链 | P0 校准工期；记录组件、状态和清理约定；至少有另一位维护者能构建、排错和审查 |

保持 API 和数据库兼容时，页面问题可通过下一版本切回旧实现，或在有相应授权时恢复上一镜像；这只恢复程序，不撤销用户在此期间产生的卡片、库存、申请或投票。仍按标准流程核对目标完整 SHA 的 CI、镜像 revision、健康、入口和备份，不跳过发布检查。

全面迁移的完成条件：现有路由和业务矩阵逐项通过；生产构建与容器检查通过；目标手机视觉验收有记录；已迁页面不再保留重复实现；团队能独立维护；保留可执行的回退说明。报告交付不等于这些条件已经满足。
